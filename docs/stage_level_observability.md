# Stage-level workflow observability

Implemented: 5 August 2026.

## Outcome

Candidate shortlisting and grounded recruiter Q&A now emit correlated,
privacy-safe stage events for validation, retrieval, database work, model calls,
and response assembly. Each run also emits one aggregate summary containing
stage counts and durations, model token usage, cached input tokens, and estimated
cost.

This is operational telemetry, not a new store of recruitment data. Events go
through the existing application logger and contain no prompt text, query text,
CV content, candidate or contact identifiers, returned records, or exception
messages.

## Correlation model

Three identifiers connect the existing telemetry layers:

- `request_id` is generated by the HTTP performance middleware and returned in
  `X-Request-ID`;
- `run_id` identifies one business workflow and matches the shortlist
  `match_run_id` where that response already exposes it; and
- `parent_run_id` links nested work, such as a recruiter Q&A run invoking a
  candidate-shortlist child run.

The same `run_id` now appears in:

- `workflow_stage` records;
- the final `workflow_summary`;
- `model_latency` records; and
- prompt/model version metadata for model-backed stages.

The HTTP `request_performance` and database `database_performance` logs retain
their existing `request_id`, while observed database connection scopes also
emit a `workflow_stage` event with the active run ID.

## Stage coverage

| Stage kind | Current examples | Recorded fields |
| --- | --- | --- |
| Validation | Input bounds, grounding checks, citation checks | Duration, rule count, input/output item counts, outcome, error type |
| Retrieval | Hybrid/graph candidate retrieval, recruiter evidence retrieval | Duration, bounded limits, retrieval mode or route intent, result counts |
| Database | Each managed Postgres connection within an observed run | Duration, operation label, outcome, error type |
| Model | Shortlist reranking and recruiter-answer synthesis | Provider, model, prompt version, model-profile version, attempt, duration, tokens, cached tokens, estimated cost |
| Response | Empty and populated response assembly | Duration and output item count |

Workflow summaries report the real end-to-end workflow duration separately from
the sum by stage kind. Stage durations can overlap—for example, a database stage
sits inside retrieval—so stage-kind totals are diagnostic breakdowns rather
than additive wall-clock time.

## Versioning

The initial observed workflows use:

- candidate shortlist workflow `1.0`;
- candidate shortlist prompt `candidate-shortlist-v1.0`;
- recruiter Q&A workflow `1.0`;
- recruiter Q&A prompt `recruiter-qa-v1.0`; and
- model profile `default-reasoning-v1` with the configured provider model name
  recorded separately.

Change the relevant version whenever prompt instructions, output contracts,
retrieval orchestration, or model-profile settings materially change. Historical
logs can then be compared without guessing which implementation produced them.

## Privacy controls

`backend/core/observability.py` enforces a narrow metric allow-list. Numeric
counts, timings, tokens, and cost are accepted; a small set of low-cardinality
labels is accepted only when it matches a bounded safe-character pattern.
Unknown fields are rejected rather than logged.

This deliberately prevents a caller from attaching fields such as:

- `query` or `question`;
- `prompt` or `response`;
- candidate, contact, company, document, or CV identifiers;
- retrieved excerpts or evidence text; and
- exception messages that may echo provider or user content.

Only the exception class name is recorded on failure.

## Event shapes

A stage event has the following content-only shape:

```json
{
  "event": "workflow_stage",
  "request_id": "request-correlation-id",
  "run_id": "workflow-run-id",
  "parent_run_id": null,
  "workflow": "candidate_shortlist",
  "workflow_version": "1.0",
  "stage": "candidate_shortlist_reranking",
  "stage_kind": "model",
  "stage_index": 4,
  "status": "success",
  "duration_ms": 825.4,
  "error_type": null,
  "metrics": {
    "provider": "openai",
    "model": "gpt-4.1-mini",
    "prompt_version": "candidate-shortlist-v1.0",
    "model_profile_version": "default-reasoning-v1",
    "input_tokens": 2500,
    "cached_input_tokens": 2176,
    "output_tokens": 180,
    "estimated_cost_usd": 0.0005
  }
}
```

The numbers above illustrate the schema; they are not a production event.

## Verification

Automated coverage proves that:

- all five stage kinds are correlated across recruiter Q&A;
- shortlist validation, retrieval, and response stages share its returned run ID;
- model telemetry contributes token, cached-token, version, latency, and cost
  metrics to the active workflow;
- managed Postgres scopes automatically create database-stage events;
- nested workflows retain `parent_run_id`; and
- content-bearing metric names are rejected and private test queries never
  appear in captured logs.

## Current boundaries

- Database timing currently measures each managed connection scope, not
  individual SQL statements or query plans. Evidence-based slow-SQL work remains
  a separate backlog item.
- Response-stage timing covers service response assembly. HTTP serialization and
  transmission remain covered by the enclosing request-performance duration.
- Log retention, dashboards, and alert thresholds depend on the deployment log
  platform; this change creates stable structured events without introducing a
  new external observability vendor or database table.
